## 0. 리뷰 목적: 기능 체크리스트가 아니라 '경험의 일치'

현재 가장 큰 위험은 **세력 지도 + 전투장 + 숫자 보상**이라는 메뉴형 구성에 머물고, 사용자가 기대한 **자유로운 우주 항해의 손맛과 생명력, 발견의 감정, 귀여운 동료와의 애착, 회화적인 플레이 무대**가 체감되지 않는 것이다. 기능 수를 계속 늘려도 재미가 자동으로 생기지 않는다.

**비전의 제품 원칙:**
1. 내가 직접 함선을 조종해 어디로 갈지 탐색하다 새 대상·위험을 **발견**한다.
2. 조우에서 선택한 위험/행동이 **전투·보상·관계**를 바꾼다.
3. 귀여운 외계 생물/동료·승무원이 화면 속에서 실제로 움직이고 반응한다.
4. 원정 보상이 **함선의 내부/제작·상점/거점**이라는 내 공간에 물리적으로 드러난다.
5. 게임의 모든 장면에서 **회화적인 깊이·살아 있는 포즈/조명**, 모바일에서 읽히는 위험·보상·터치 대상의 대비가 일관된다.

## 2. 다음 개발 실행에 줄 최상위 시정명령

### P0-VISION-001 — 고정 두 웨이브 행성 경기장을 '발견 가능한 원정 한 곳'으로 교체 (첫 시정 변경 하나)

**문제:** 지금은 서로 다른 항성에 도착해도 전투장이 같은 구조이고, 전리품 숫자만 다르다. 사용자가 말한 '탐험의 재미 없음'과 가장 직접적으로 연결됨. 세력/상점·덱 수치를 추가하면 빗나감.

**가설:** 60–120초 원정의 **왼쪽 조우/구조 경로 vs 오른쪽 고위험·고보상 전투 경로**가 실제 화면/터치 선택과 상태 변화를 만들면, 최소한 '탐색할 선택'이 생긴다. 장면 도달·공간 이동(그냥 메뉴 분기 선택으로 대체 금지)이 핵심.

**최소 구현 스코프** (한 번에 완성하기 어려우면 경로의 **실제 이동/선택**만 이번 시간에 구현해 단계별 완료 상태 표시):
- 지금의 `start_run() → spawn_wave()` 자동 진입 대신, 적이 아직 없는 **탐색 화면**에서 플레이어가 어느 쪽을 탐사할지 직접 **움직여서 결정**한다. 기존 드래그/스와이프를 유지; 새로운 메뉴 버튼만 추가하지 않음.
- 왼쪽은 위험이 적은 외계 생물 흔적, 오른쪽은 위험 신호가 읽히는 광물/적 경고. **각 경로를 실제 플레이어 위치와 충돌/상호작용으로 선택**하고, 한 번에 분명한 보상을 준다.
- **선택 결과를 게임상태에 기록**하여 귀환시 플레이어가 어떤 길을 택했고 무엇을 얻었는지 알게 한다. 새 귀여운 생물 Nooli의 영입·배치는 후속이지만 이번 단계에 보여준 시각 동료가 실제 상호작용이 없다면 '완료'라고 쓰지 않음.
- 참고작은 [Absolum](https://playabsolum.com/) **분기·위협 전조** + [Dave the Diver](https://www.mintrocketgames.com/) **탐험/발견/회수의 이유** 두 개만. 기존 상용 게임 배경·캐릭터/에셋 직접 사용 금지.
- 디자인 세션은 [PR #4: Veilwood/Nooli](https://github.com/syjkim0125/harvest-deck/pull/4)의 **별개 소스 에셋** 중 조명/실루엣/양방향 위험 사인만 먼저 참고해 단순화한 별도 게임용 레이어를 준비. PR 전체를 테스트 없이 main 병합하지 않는다.

**최소 자동 수용 테스트:** 서로 다른 좌/우 지역으로 실제 이동하면 서로 다른 경로·조우·보상 상태가 재현된다; 헛터치나 HUD 탭은 선택을 발동하지 않는다; 360×640과 393×852 범위에서 현재 터치 공격/회피 조작을 방해하지 않는다; 전투 종료 후 선택/보상 보존; legacy 브랜치 변경 없음.

**반드시 사람 확인:** 게임 스크린 녹화와 처음 보는 플레이어의 '어디로 가고 싶나/무엇을 발견했나' 설명. 실제로 움직여 탐험했다고 느끼는지 판단. 컴파일/CI만으로 완료하지 않음.

## 3. 반복 리뷰의 판단 규칙 (토큰 낭비·중복 방지)

1. 매번 `main` SHA와 관련 PR merge 상태가 **직전 리뷰와 같은지** 확인. 같으면 수용 테스트/위험/미검증 상태만 짧게 기록하거나 중복 보고하지 않음.
2. 변경이 있으면 한 기능만 현재 실제 플레이 영상/캡처(가능할 때) vs 참조 1–2개 vs 비전의 의미 있는 **플레이 행동**으로 비교.
3. **완료 판정:** 코드 있음 ≠ UI 노출 ≠ 실제 조작됨 ≠ 재미 검증됨. `PLANNED / CODED / CI / PLAYABLE / USER-VERIFIED` 구분.
4. 리뷰는 **P0 최대 2개와 이번 시간 개발 하나**로 제한. 우주항행/전투/동료/제작 등을 동시에 구현하라 지시하지 않음.
5. 이전 구 과일·체인소 자동사냥 리뷰는 역사 기록이며 최신 SF 제품 방향의 지시가 아님.
6. 디자인 세션은 제안 PR만, 기능 개발 세션은 코드·테스트·main/Pages 통합 담당. 리뷰 자체는 GitHub 메모/과제 전달, 게임 코드 임의 변경 금지.
